# 🚪 Doorman

**Обратный прокси с веб-админкой для самостоятельного хостинга.** Направьте много доменов на один сервер (порты 80/443) и укажите в админке, на какой внутренний `IP:порт` отправлять каждый домен. Сертификаты выпускаются и продлеваются автоматически.

[English](README.md) · Русский

```
app.example.com  ─┐
crm.example.com  ─┼─▶  Doorman :80/:443  ─▶  192.168.1.10:3000
wiki.example.com ─┘    (Caddy + админка)  ─▶  192.168.1.20:8080
                                          ─▶  192.168.1.30:80
```

## Возможности

- Добавление, изменение, отключение и удаление маршрутов `домен → IP:порт` в веб-интерфейсе
- Автоматический HTTPS: Let's Encrypt для публичных доменов, внутренний CA Caddy для приватных
- Изменения применяются на лету, без перезапусков и обрывов соединений
- Индикатор доступности каждого сервиса
- HTTP и HTTPS на стороне сервиса, WebSocket и HTTP/3 из коробки
- Настройки переживают перезапуск и лежат в двух Docker-томах
- Лёгкий: Caddy и небольшое приложение на FastAPI (около 100 МБ RAM)

## Быстрый старт

```bash
git clone https://github.com/BobJustFry/doorman.git
cd doorman
cp .env.example .env      # задайте ADMIN_PASSWORD
docker compose up -d --build
```

Админка открывается по адресу <http://127.0.0.1:8080>. На удалённом сервере используйте SSH-туннель:

```bash
ssh -L 8080:127.0.0.1:8080 user@your-server
```

Либо укажите `ADMIN_DOMAIN=panel.example.com` в `.env`, и админка будет доступна по HTTPS (домен должен указывать на сервер).

## Требования

- Docker с плагином Compose
- Свободные порты 80 и 443 на хосте
- Для публичных сертификатов: A-записи доменов указывают на сервер
- Сервер должен достучаться до ваших сервисов. Если офис за NAT, соедините сервер с локальной сетью через VPN (например, WireGuard).

## Настройки

| Переменная | По умолчанию | Описание |
|---|---|---|
| `ADMIN_PASSWORD` | обязательна | Пароль админки |
| `ADMIN_DOMAIN` | пусто | Домен, на котором админка открывается по HTTPS |
| `ADMIN_TLS` | auto | `auto` (Let's Encrypt) or `internal` (Caddy CA) for the admin domain |
| `ACME_EMAIL` | пусто | E-mail для уведомлений Let's Encrypt |
| `HTTP_PORT` / `HTTPS_PORT` | 80 / 443 | Порты хоста для прокси |
| `ADMIN_PORT` | 8080 | Локальный порт админки (только 127.0.0.1) |

## Дополнительные порты

Кроме 80/443 маршрут можно опубликовать на дополнительных портах (например, `alex.example.com:8444`). Откройте **Routes → Edit → Advanced → Extra ports** и добавьте порт. Он пробрасывается 1 в 1: публичный порт `8444` идёт на порт `8444` сервиса. Отметьте *HTTPS upstream*, если на этом порту сервис работает по TLS.

Для каждого дополнительного порта также нужно пробросить его на роутере на сервер с Doorman.

Файрвол сервера может следовать за маршрутами автоматически. Один раз установите небольшого помощника (нужны `ufw` и root):

```bash
sudo bash deploy/install-firewall-sync.sh
```

Дальше админка публикует используемые порты, а служба systemd открывает и закрывает соответствующие правила `ufw` (с пометкой `doorman-route`; остальные ваши правила не затрагиваются). Без помощника порты открывайте сами: `sudo ufw allow 8444/tcp`.

Caddy работает в режиме `network_mode: host`, поэтому может слушать любой порт без правки `docker-compose.yml`. Это работает только на Linux (Docker Desktop на Windows/macOS для продакшена не подходит). Побочный плюс: сервисы на самом сервере Doorman доступны как `127.0.0.1:ПОРТ`.

## Заглушка и защита от сканеров

Любой хост без маршрута получает дружелюбную страницу «Nobody's home» (HTTP 404) вместо пустого ответа: на порту 80 и по HTTPS, в том числе при открытии сервера по голому IP. Для HTTPS сертификаты для неизвестных имён выпускает внутренний CA только в зонах ваших маршрутов (например, `*.example.com`, если у `app.example.com` есть маршрут) и не более 1000 имён, поэтому случайные имена сканеров не заставят сервер бесконечно выпускать сертификаты. Остальным именам рукопожатие отклоняется.

Админка пишет подозрительные события (неверный пароль, запросы к хостам без маршрута, пути, которые просят только сканеры, например `/.env`) в `security.log` в формате `<epoch> doorman-<тип> ip=<адрес>`. Один раз установите джейлы fail2ban, и нарушители будут блокироваться через `ufw`:

```bash
sudo bash deploy/install-fail2ban.sh
```

| Джейл | Срабатывает | Бан |
|---|---|---|
| `doorman-auth` | 5 неверных паролей за 10 мин | 1 час |
| `doorman-stub` | 15 запросов к неизвестным хостам за 10 мин | 12 часов |
| `doorman-probe` | 3 «сканерских» пути за 10 мин | 24 часа |

Частные сети (`10/8`, `172.16/12`, `192.168/16`) и localhost никогда не банятся. Список банов: `sudo fail2ban-client status doorman-stub`.

## Сертификаты

Для каждого маршрута выбирается режим:

- **Let's Encrypt (public)**: для реальных доменов, которые из интернета указывают на этот сервер.
- **Internal CA**: для приватных имён. Браузеры будут предупреждать, пока вы не добавите корневой сертификат Caddy в доверенные (`docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt .`).

## Split DNS

Внутри офиса направьте те же домены на Doorman (внутренний DNS, роутер или `hosts`). Тогда все клиенты используют одни и те же сертификаты и маршруты.

## Безопасность

- API администрирования Caddy (`:2019`) доступно только внутри Docker-сети и наружу не публикуется.
- Админка привязана к `127.0.0.1`, пока вы не задали `ADMIN_DOMAIN`. Используйте длинный `ADMIN_PASSWORD`; неудачные входы ограничиваются по частоте.
- Сертификаты HTTPS на стороне сервисов не проверяются (обычно это внутренние сервисы с самоподписанными сертификатами).
